# 需求收集方法论 (Requirements Gathering Methodology)

> **本文件是 `eas-planning-writer` 阶段 1（需求与发现）的完整方法论支撑。** task_plan.md 阶段 1 仅保留速查入口与勾选清单，详细问句库、分支模板与执行规范全部在本文件。
>
> **[MUST] 本阶段 MUST 不可整段跳过。** 仅当用户提供完整 PRD/Spec 或引用既有规范时，可压缩轮次但 MUST 保留方法论骨架。`task_profile` MUST 满足 [第六章退出条件](#六退出条件与跳过规则-exit--skip-rules) 后方可进入阶段 2。

---

## 一、为什么需要方法论 (Why a Methodology)

仅凭直觉提问会导致三类典型失败：

1. **问题太空**：用户答"我想要一个规划任务"——无法进入阶段 2
2. **问题太散**：提了 10 个题但彼此无逻辑关联，需求画像模糊
3. **问题遗漏**：未问边界/反例，做出来才发现关键场景未覆盖

**方法论的目标**：让 Agent 像**结构化访谈员**一样提问，而不是闲聊。

---

## 二、主框架选择：苏格拉底式六维度 (Primary Framework)

**结论**：本技能统一采用 **苏格拉底式提问法（Socratic Questioning）** 作为主框架。

### 六维度定义（顶层骨架）

| # | 维度 | 核心动作 | 在本技能阶段 1 中的目标 |
|---|---|---|---|
| 1 | **澄清问题 (Clarify)** | 明确概念边界 | 用 1 句话定义任务 + 列出具体使用场景 |
| 2 | **探究假设 (Probe Assumptions)** | 检验前提 | 暴露硬约束（时间/资源/技术/合规）+ 必要性论证 |
| 3 | **挖掘证据 (Evidence)** | 收集具体例子 | 得到 5+ 触发短语（用户原话）+ 标注对应场景 |
| 4 | **视角探索 (Perspectives)** | 换位思考 | 发现边界用例（不应纳入）+ 相关方清单（谁参与/谁 Review） |
| 5 | **后果分析 (Consequences)** | 推演影响 | 定义失败兜底策略 + 估算阶段数与跨 session 次数 |
| 6 | **反思完整性 (Reflection)** | 自我审视 | 跨领域相关方清单 + 遗漏检查（"还有什么没说但重要"） |

**关键原则**：
- 六维度**不必每轮都全用**，按需选 1-2 个维度
- 维度顺序可灵活调整，但**澄清问题必须先于其他维度**
- 每个维度至少产出**一个可验证的产物**（场景列表 / 约束清单 / 触发短语集 等）

## 三、领域分支：按任务类型选用问句模板 (Domain Branches)

不同领域的长任务，在同一维度下的**具体问句**差异极大。主框架是骨架，领域模板是血肉。

### 3.1 领域识别 (Domain Detection)

进入提问前，先用一句话判断领域（影响后续问题模板）：

| 领域 | 识别信号 | 典型任务示例 |
|---|---|---|
| **Code / 工程** | 用户提到 API、库、SDK、构建、测试 | 重构支付模块、接入新 SDK |
| **Design / 体验** | 用户提到界面、交互、视觉、可用性 | 重设计仪表盘、暗色模式 |
| **Writing / 创作** | 用户提到文档、报告、文案、内容 | 写产品白皮书、技术博客 |
| **Business / 流程** | 用户提到合规、审查、决策、运营 | 合规改造、SOP 梳理 |
| **Data / 分析** | 用户提到数据、指标、报表、查询 | 报表重构、数据迁移 |
| **Hybrid** | 跨领域，需要多模板组合 | 全栈改造（code + writing） |

**判断时机**：在维度 1（澄清问题）的第一题 MUST 调用宿主 Agent 的「结构化提问工具」询问领域。

### 3.2 通用模板 vs 领域模板

每个领域都按六维度组织**问句模板**：

- **通用模板（必问）**：每个领域都问，作为最低基线
- **领域模板（按需选用）**：根据领域加载，进一步细化

#### 通用模板（6 题，覆盖六维度各 1 题）

```
D1 澄清：这项任务具体要解决什么场景？给一个你马上会去做的事。
D2 假设：你为什么需要专门做这件事，而不是用现有方案？
D3 证据：能举 3 个你（或团队）会说的话（触发短语）吗？
D4 视角：哪些角色会参与/受影响？他们的关注点有何不同？
D5 后果：如果这件事只能完成 80%，剩下 20% 会发生什么？
D6 反思：还有什么我们没讨论到但你认为重要的？
```

#### Code / 工程 领域追加模板

```
D1+：涉及哪些库/SDK/服务？版本号？
D2+：调用频率？是同步阻塞还是异步流式？
D3+：典型输入输出是什么类型？有没有副作用？
D4+：错误处理策略？是否需要重试 / 超时 / 降级？
D5+：是否需要缓存、幂等性、并发控制？
D6+：测试覆盖要求？是否有 mock 数据需要预置？
```

#### Design / 体验 领域追加模板

```
D1+：面向设计师、用户、还是开发者？使用设备？
D2+：交互形态是 Web、桌面、还是移动？响应式要求？
D3+：视觉风格基调（极简/品牌化/中性）？有无既有设计系统？
D4+：可访问性要求（WCAG 等级）？多语言支持？
D5+：失败状态如何呈现（空状态/错误状态/加载状态）？
D6+：是否需要可定制主题、白标、暗色模式？
```

#### Writing / 创作 领域追加模板

```
D1+：目标读者是谁？技术背景如何？预期阅读时长？
D2+：语气基调（正式/对话/学术/营销）？是否需要一致的声音？
D3+：输出长度约束（字数/段落数/章节数）？固定结构还是灵活？
D4+：是否引用外部资料？是否需要引用格式（脚注/链接/APA）？
D5+：是否需要 SEO 关键词覆盖？是否多语言版本？
D6+：质量验收标准（可读性评分/语法检查/事实核查）？
```

#### Business / 流程 领域追加模板

```
D1+：适用法规/标准/内部制度是什么？版本与生效日期？
D2+：决策者是个人还是委员会？是否需要审批流？
D3+：关键时间节点与 SLA？是否有时效性要求？
D4+：相关方有哪些（业务/法务/合规/客户）？冲突如何仲裁？
D5+：违规后果是什么？是否需要兜底回退？
D6+：是否需要审计日志、留痕、签名？
```

#### Data / 分析 领域追加模板

```
D1+：数据源是什么（数据库/API/文件）？规模与更新频率？
D2+：指标定义的口径是什么？是否多版本？
D3+：输出形式（表格/图表/JSON/报告）？消费方是谁？
D4+：权限与脱敏要求？敏感字段如何处理？
D5+：异常值/缺失值策略？口径冲突如何归因？
D6+：是否需要版本化、可复现、追溯？
```

#### Hybrid 组合

当任务跨领域时，**合并多套领域模板**，按"主领域 + 副领域"标记：

```
示例：全栈改造 (Code + Writing)
- 主：Code 模板（D1+ 至 D6+）
- 副：Writing 模板（D3+ 输出长度、D4+ 引用格式）
```

## 四、轮次策略 (Rounds Strategy)

**核心原则**：轮次与任务复杂度正相关，不要一刀切。

| 任务复杂度 | 判据 | 推荐轮次 | 每轮题数 |
|---|---|---|---|
| **简单**（单领域、<5 阶段） | 1 个明确场景、<5 个触发短语 | **1 轮** | 3-4 题 |
| **中等**（多领域 / 跨部门） | 2-3 个场景、需明确边界 | **2 轮** | 3-4 题/轮 |
| **复杂**（跨领域 / 跨 session） | 多角色、多边界、需持久化 | **3+ 轮** | 4 题/轮，第二轮起聚焦边界 |

**轮次结构**：

```
第 1 轮（场景构建）
  ├─ 维度1 澄清：领域 + 核心场景
  ├─ 维度3 证据：触发短语 + 用户原话
  └─ 维度2 假设：用户为何选择做这件事

第 2 轮（约束与边界，条件触发）
  ├─ 维度2 假设：领域专属约束
  ├─ 维度4 视角：相关方与冲突
  └─ 维度5 后果：失败兜底

第 3 轮（完整性验证，可选）
  ├─ 维度6 反思：遗漏检查
  └─ 维度5 后果：阶段切分与兜底
```

## 五、提问工具规范 (Asking Tool Discipline)

**[MUST] 调用宿主 Agent 的「结构化提问工具」（structured-question tool）**，MUST NOT 仅靠自由文本对话提开放问题。

### 5.1 工具抽象与框架名称映射

不同 Agent 框架下，结构化提问工具的名称与签名不同。Agent MUST 按本机环境识别后调用，调用参数 MUST 包含：

| 参数 | 必填 | 说明 |
|---|---|---|
| `question` / `prompt` / `text` | MUST | 问题文本 |
| `options` / `choices` | MUST | 2-4 个互斥选项 |
| `recommended` / `default` | SHOULD | 推荐项索引或标签 |
| `multi_select` | MAY | 是否允许多选 |

**主流 Agent 框架的别名映射**（Agent MUST 按本机识别）：

| 框架 / 平台 | 工具名 | 备注 |
|---|---|---|
| Trae IDE / Claude Code / Cursor | `AskUserQuestion` | 本仓库当前主流 |
| OpenAI Agents SDK | `AskUserChoice` / `input_required` | 参数命名略不同 |
| 自研 Agent 框架 | `request_user_input` / `user_confirm` | 视框架而定 |
| LangGraph / CrewAI | 通常以 `Tool` 形式暴露，名称 `ask_user` 或类似 | 视实现而定 |

**退化策略**：若宿主环境未提供结构化提问工具，MUST 退化为"分段对话 + 主动声明每段答案"，但仍 MUST 遵守下方选项设计与轮次策略（即每段必须显式给出 2-4 个候选答案 + 1 个推荐）。

### 5.2 选项设计规则

- **每题 MUST 提供 2-4 个互斥选项**
- **SHOULD 标识推荐项**（label 后加「（推荐）」）
- **选项 MUST 互斥**，避免"以上都是"
- **MUST 预留一个自定义输入**（捕获遗漏，系统通常自动加 "Other"）

### 5.3 推荐项策略

提问时 MUST 主动给出推荐——用户一键确认即可，不要让用户每次都做艰难选择。

### 5.4 反模式（MUST 避免）

- ❌ 仅靠自由对话提开放问题（用户答非所问）
- ❌ 一题超过 4 个选项（工具上限）
- ❌ 全是"以上都对 / 以上都不对"的安全选项
- ❌ 第一题直接问实施细节（应先维度 1 澄清任务）
- ❌ 跳过维度 1 直接问细节
- ❌ 同维度重复提问（信息冗余）

## 六、退出条件与跳过规则 (Exit & Skip Rules)

### 6.1 [MUST] 退出条件

需求画像 MUST 同时满足以下 4 项才能进入阶段 2，缺一不可：

- [ ] **[MUST] 场景明确**：能用 3 个具体使用场景描述任务
- [ ] **[MUST] 触发短语**：已列出 5+ 触发短语（用户原话或近似表达）
- [ ] **[MUST] 边界用例**：已识别至少 1 个不应纳入本任务的场景
- [ ] **[MUST] 兜底策略**：失败（数据缺失/工具失败/上下文爆炸）时有明确的应对路径

**[MUST-NOT]** 未满足全部 4 项时 Agent MUST NOT 进入阶段 2，必然返工。

### 6.2 [MUST-NOT] 整段跳过规则

**[MUST-NOT] 本阶段 MUST NOT 整段省略。** 仅允许在保留方法论骨架的前提下**压缩轮次**。

满足以下任一条件时，可压缩（如从多轮压到 1 轮内一次性抛出 3-4 题）但 MUST NOT 完全跳过：

| 条件 | 证据形式 |
|---|---|
| 用户提供完整 PRD/Spec | 文件链接或内联内容 |
| 用户明确说"照这个文档做" | 直接引用既有规范 |
| 任务是已有任务的小幅修改 | 引用原任务名 + 变更点 |

### 6.3 [MUST] 暂停规则

遇到以下情况，Agent MUST 暂停流程并退出，等待下次触发：

| 用户响应 | Agent 动作 |
|---|---|
| "我再想想" / "等一下" | MUST 退出，等待下次触发 |
| "我也不知道" | MUST 给出 2-3 个常见模式作为默认假设，让用户挑 |
| "你建议" | MUST 用 JTBD 视角给出 1-2 个候选场景，让用户确认 |

**[MUST]** 用户响应属于暂停类时，Agent MUST 暂停而非强行推进；MUST NOT 在需求不清时强行进入阶段 2。

## 七、产出物登记 (Deliverables Registry)

**[MUST] 阶段 1 结束时 Agent MUST 在内部维护 `task_profile`**，作为后续阶段 2-5 的唯一可信输入。

### 7.1 task_profile 结构

```yaml
# 任务画像（仅 Agent 内部使用，可选择性写入 findings.md 顶部）
task_profile:
  domain: code | design | writing | business | data | hybrid   # [MUST]
  scenarios: [<3+ 具体使用场景>]                                # [MUST]
  triggers: [<5+ 触发短语>]                                    # [MUST]
  boundaries: [<不应纳入本任务的场景>]                          # [MUST]
  constraints:                                                  # [SHOULD]
    - <硬约束，如"必须支持 Windows">
  assumptions:                                                  # [SHOULD]
    - <已验证的假设>
  fallback_strategy:                                            # [MUST]
    data_missing: <数据缺失时如何兜底>
    tool_failure: <工具调用失败时如何兜底>
    context_overflow: <上下文爆炸时如何兜底>
  estimated_phases: <3-15>                                     # [MUST]
  cross_session: <true | false>                                 # [MUST]
  rounds_used: <实际提问轮次>                                   # [MUST]
  compressed: <true | false>                                    # [MUST]
  compressed_reason: <若压缩，引用 PRD/Spec/原任务名>            # [MAY]
```

### 7.2 [MUST] 自检清单（阶段 1 → 阶段 2 切换前）

Agent MUST 在切换前逐项校验，全部满足方可推进：

- [ ] 6.1 退出条件 4 项 MUST 全打勾
- [ ] `task_profile` 字段全部填写（必填项非空）
- [ ] 已记录 `rounds_used` 与 `compressed` 标记
- [ ] 已识别领域并加载对应问句模板
- [ ] 已估算阶段数与跨 session 次数（喂给阶段 2 的阶段切分）
- [ ] 已给出失败兜底策略（喂给阶段 2-5 的失败处理）
- [ ] `findings.md` 顶部已固化 task_profile 四段（需求 / 触发短语 / 边界 / 兜底）
- [ ] `0001-initial-design.md` 决策文档已落地（9 章节完整）

**[MUST-NOT]** 自检未通过时 MUST NOT 进入阶段 2，MUST 回退补问。

## 八、与阶段 2-5 的衔接 (Handoff)

| 阶段 1 产出 | 阶段 2 输入 | 阶段 3-5 输入 |
|---|---|---|
| `domain` | 选择对应阶段模板 | 选择实施工具与脚本 |
| `scenarios` + `triggers` | task_plan 阶段草案 | 阶段特定内容填充 |
| `boundaries` | 排除清单 | 反模式/边界检查 |
| `constraints` | 自由度级别选择 | 脚本与模板设计 |
| `fallback_strategy` | 失败处理三要素 | 阶段 4 测试与验证 |
| `estimated_phases` + `cross_session` | 阶段切分粒度 | task_plan.md 阶段定义 |

**铁律**：**阶段 1 的产出是后续所有阶段的唯一可信输入**。若阶段 2 发现阶段 1 产出不足，**必须回退到阶段 1 补问**，不得"先做着试试"。

## 九、完整示例：3 轮提问示范 (Worked Example)

### 用户原始请求

> "我想用规划技能写一份产品周报"

### 第 1 轮（场景构建，4 题）

```
Q1 [维度1 澄清 · 领域识别]
"这份周报面向哪种场景？"
选项：
  - 团队内部技术周报 (推荐)
  - 业务/运营周报
  - 高管汇报周报
  - 客户/对外周报

Q2 [维度3 证据 · 触发短语]
"用户/团队可能会说哪些话来启动这个任务？"
（自定义输入，收集 5+ 短语）

Q3 [维度2 假设 · 必要性]
"为什么不直接用 Word/Notion 模板，而要用规划技能？"
选项：
  - 需要跨 session 持续记录进度 (推荐)
  - 需要结构化的"决策/错误"日志便于 Review
  - 需要接入 Git/CI 等自动化检查
  - 需要团队统一模板与可追溯性

Q4 [维度1 澄清 · 输出形态]
"期望的周报结构是？"
选项：
  - 固定 5 段：目标 / 进展 / 决策 / 风险 / 下周 (推荐)
  - 灵活大纲（按需增减）
  - 数据看板为主，文字为辅
```

### 第 2 轮（约束与边界，3 题）

```
Q5 [维度2 假设 · 领域约束]
"周报需要包含哪些量化指标？"
选项：
  - 必须含数字指标（达成率/工时） (推荐)
  - 文字描述为主
  - 图表截图即可
  - 完全自定义

Q6 [维度4 视角 · 相关方]
"周报的读者/审批流是怎样的？"
选项：
  - 直属 leader 1 人 Review
  - 团队周会共享
  - 多级审批链
  - 仅个人归档 (推荐：MVP 优先)

Q7 [维度5 后果 · 失败兜底]
"如果某项数据缺失怎么办？"
选项：
  - 标注"暂无数据"继续推进 (推荐)
  - 暂停任务等用户补齐
  - 用历史数据兜底
```

### 第 3 轮（完整性验证，2 题）

```
Q8 [维度6 反思 · 边界用例]
"哪些场景下应该拒绝触发？（多选）"
```
